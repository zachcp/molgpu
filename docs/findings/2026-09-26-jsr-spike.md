# JSR for every package: feasibility spike

Bead `molgpu-sept-0lg.1`. The question was whether all seven `@molgpu/*`
packages can be TypeScript source published to [JSR](https://jsr.io), and
whether anything makes that impossible. The retired experiment used a Deno
workspace with a full TypeScript port of `@molgpu/table`, a TypeScript port of
the viewer's point-rendering path, probes, and a browser render test.

**Answer: nothing blocks it.** Every technical question came back yes. The
problems are all in dependency metadata, because JSR has no peer dependencies.
Three design changes resolve them (below). Recommendation: go with JSR for
everything (option C), with those changes.

> **Correction (2026-09-26, during the io conversion):** the computed-specifier
> approach to keeping Mol* optional (§1, recommendation 3) works in Deno but
> breaks bundlers. Vite and webpack cannot see through
> `import(`${spec}/lib/...`)`, and browsers cannot resolve the bare specifier at
> runtime. Mol* became a regular dependency of `io` instead, imported lazily
> with literal specifiers. See `packages/io/README.md`.

## What JSR changes

### 1. No peer dependencies (jsr-io/jsr#880, still open)

JSR treats every dependency as a regular dependency. The maintainers' position
(#880, #332) is that a dependency with a broad range behaves like a peer, since
npm 7+ installs peers anyway and dedupes compatible ranges. That covers most of
what this repo uses peers for, but not all of it:

- **`@molgpu/table` as a single shared copy (x24.12).** Becomes
  `jsr:@molgpu/table@^0.1.0` in each dependent. A broad caret range dedupes in
  Deno and in npm, so the rule still holds.
- **use.gpu pinned to exactly 0.20.0.** Becomes a regular
  `npm:@use-gpu/*@0.20.0` dependency. It dedupes when the app also resolves
  0.20.0, which is today's only 0.20 release. The difference: if an app pins a
  different use.gpu version, npm installs a second copy silently instead of
  failing with a peer conflict. Two copies of `@use-gpu/live` break Live
  contexts. **Change:** add a runtime guard that fails loudly when the viewer's
  Live instance is not the one rendering it, and document the pin prominently.
- **Mol\* as an optional peer of `io`.** There is no optional-dependency
  mechanism (#301, #1147). A literal `import('npm:molstar/...')` would make Mol*
  a hard dependency of `io`, and through `io` of the viewer too: 80 MB unpacked,
  plus express, swagger-ui and more. **Change:** load Mol* through a computed
  specifier. `deno publish` accepts it with an `unanalyzable-dynamic-import`
  warning and records no dependency. The specifier must resolve without an
  import map, so use `npm:molstar@^5.11.0` under Deno (verified: Deno fetches it
  only on first call) and bare `molstar` elsewhere (resolved from the app's own
  install). A cleaner alternative is to let callers pass the Mol* module in.

### 2. use.gpu has no `exports` field and no `"type": "module"`

Deno's runtime (like Node's) follows `main` to use.gpu's CommonJS build, and its
re-export helpers hide named exports:
`import { makeContext } from
'@use-gpu/live'` fails at runtime under `deno run`.
Bundlers read `module` and get the ESM build, and the viewer only runs in a
browser, so this affects only Node/Deno-side tests that import use.gpu. None do
today. Keep pure logic out of modules that import use.gpu, as the repo already
does. `timeline`'s deep `mjs/ease.mjs` import is the existing workaround and
still works.

### 3. Import mechanics

- Relative imports carry `.ts` extensions. npm/use.gpu/Mol* imports go through
  each package's `deno.json` `imports` map, which JSR rewrites at publish.
- Global types (`GPUBuffer`, etc.) come from `@webgpu/types`, set in
  `compilerOptions.types`. Check that the generated npm `.d.ts` still reaches
  them (see below).
- `use(Component, props)` does not infer render-callback parameter types, so
  callbacks need explicit annotations. JSX in consumer code is unaffected.

## Not verified

- **npm users through JSR's compatibility layer** (`npx jsr add`, which serves
  `@jsr/molgpu__viewer` from `npm.jsr.io`). This can't be exercised without a
  real publish. JSR generates transpiled JS plus `.d.ts` from the TypeScript
  source. A fallback exists if it disappoints: dual-publish to npm with
  [dnt](https://jsr.io/@deno/dnt), which would also restore real
  `peerDependencies` for npm users.
- The full viewer (materials, OIT, picking, glyph/font workers) under
  `deno bundle`. Only the point path was bundled. Vite stays available for the
  browser suites either way.

## Recommendation

Option C: JSR for all seven packages, with:

1. every internal dependency as `jsr:@molgpu/<name>@^x.y.z` (broad range);
2. use.gpu as exact `npm:` pins, plus a runtime duplicate-Live guard;
3. Mol* loaded through a computed specifier or an injected module, so it stays
   optional;
4. tests unchanged in shape: `node --test` runs `.ts` directly, and so does
   `deno test`, so CI can run both.

npm users get JSR's npm compatibility layer. Dual-publishing via dnt stays
available as a fallback, not a starting point.
